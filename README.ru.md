# ReviveGuard

Лёгкий аудитор безопасности Linux-серверов с (планируемым) контролируемым автоисправлением.

> **Статус: ранняя разработка (0.1.0.dev0).** Реализован только аудит настроек SSH в режиме
> «только чтение». Не готов к production, проверка безопасности не проводилась.
> English version: [README.md](README.md).

## Что работает сейчас

- `reviveguard audit` — только чтение, систему не изменяет.
- Проверки SSH `SSH-001`..`SSH-005`: вход root, парольная аутентификация, пустые пароли,
  аутентификация по ключу, владелец и права `sshd_config`.
- Проверки файрвола `FW-001`..`FW-004` (UFW, nftables, iptables, firewalld) — только находки;
  изменения файрвола всегда вручную. Проверки fail2ban `F2B-001`..`F2B-005`; отсутствующий
  SSH-jail (`F2B-002`) `fix` может включить. Обоим модулям нужен root.
- `reviveguard fix [--category ssh] [--check SSH-002]` — интерактивные исправления для находок SSH
  (нужен root). Каждое исправление объясняется, бэкапится, подтверждается вами, проверяется и
  записывается; при сбое исходные файлы восстанавливаются автоматически.
- `reviveguard history` / `reviveguard rollback [--id FIX-YYYY-NNN] [--yes]` — хранилище бэкапов
  и откат (для будущих исправлений; покрыто тестами, но пока ни одно исправление не создаёт операций).
- Вывод на русском и английском (`--lang ru|en`), текстом или в JSON.

## Пока не реализовано

`fix --auto`, `report`, `config set`, а также проверки Docker, обновлений,
прав доступа, сервисов и sysctl.

## Требования и проверенные платформы

- Python 3.11+, только стандартная библиотека.
- Цель: Debian 12+, Ubuntu 22.04+. Разработка и тесты пока выполнялись только на Ubuntu 24.04;
  другие системы не проверялись.

## Установка и запуск

```bash
pip install -e .
reviveguard audit
reviveguard --lang ru audit
reviveguard audit --format json
sudo reviveguard audit   # с правами root результаты по SSH точнее (sshd -T)
```

Без root настройки читаются из `/etc/ssh/sshd_config` (с поддержкой `Include` и значениями
OpenSSH по умолчанию); в отчёте указан использованный источник.

## Конфигурация

TOML: `/etc/reviveguard/config.toml` или `--config ФАЙЛ`, пример — `examples/config.toml`.
Неизвестные ключи отвергаются. Приоритет языка: `--lang`, `language` в конфиге, локаль `LANG`, английский.

## Безопасность исправлений SSH

- Исправления добавляют небольшой drop-in (`/etc/ssh/sshd_config.d/00-reviveguard-<параметр>.conf`),
  а не переписывают `sshd_config`. Отмена: `reviveguard rollback` (или удалить файл).
- Порядок: предпроверки (текущая конфигурация проходит `sshd -t`, есть `Include`, root, поддерживаемая ОС) →
  бэкап → запись → `sshd -t` → **reload** (не restart) → повторная проверка → запись в историю.
  Сбой на любом шаге восстанавливает копию; если не удалось и восстановление, будет явная
  инструкция выполнить `reviveguard rollback --id ...`.
- Изменение входа root и парольной аутентификации требует отдельного ввода `yes` и **отклоняется
  (ручное исправление)**, если не подтверждена альтернатива: при удалённой сессии *текущий
  пользователь* должен иметь валидный `authorized_keys` (права, как требует `StrictModes`), не быть
  запрещён правилами `AllowUsers`/`AllowGroups`/`Deny*`, а `AuthenticationMethods` должен быть по умолчанию.
  Для удалённой сессии root ставится только `prohibit-password` и только если у root есть ключ.
- Сервер не может доказать, что клиентский ключ реально работает; проверяются перечисленные
  предпосылки. **Держите открытой вторую SSH-сессию** при применении рискованных исправлений.

## Бэкап и откат

Состояние хранится в `/var/lib/reviveguard` (`backups/`, `history/`, `reports/`, `config/`; права 0700;
можно переопределить через `--state-dir`). Перед изменением файла исправление сохраняет его
содержимое, права и владельца с контрольной суммой SHA-256 и записывает операцию (ID проверки и
исправления, планируемое изменение) *до* самого изменения, поэтому прерванную операцию тоже можно откатить.

`rollback` показывает, что будет восстановлено, предупреждает о правках после исправления,
проверяет контрольную сумму, запрашивает подтверждение (или `--yes`), восстанавливает только файлы
этой операции и проверяет содержимое, права и владельца. Сервисы он **не** перезапускает: после
отката конфигурации службы перезагрузите её сами.

Ограничения: обновления пакетов и изменения внешних сервисов нельзя надёжно откатить — такие операции
будут помечаться как необратимые; символические ссылки отвергаются, а не копируются.

## Модель безопасности и ограничения

- Исправления SSH и fail2ban покрыты тестами с имитацией системы, но **не** запускались на
  реальных `sshd`/`fail2ban`/`systemd` (см. [docs/vps-testing.ru.md](docs/vps-testing.ru.md)).
  В Ubuntu 22.04 системный Python 3.10, нужен 3.11+.  Сначала попробуйте на некритичной машине. `fix --auto` не реализован.

- Режим аудита только читает данные; это проверяется тестом.
- Команды запускаются списком аргументов (без shell) с таймаутами.
- В отчёты попадают значения настроек, но не секреты.
- Будущие исправления не будут менять доступ (SSH, firewall) без бэкапа, проверки,
  верификации и явного подтверждения. Обновления пакетов откатить нельзя — это будет указано явно.
- Блоки `Match` в `sshd_config` не вычисляются; проверяются только глобальные настройки.
